# Pina Studio 日次運営チェックリスト

個人運営で見落としを防ぐための、最小限の確認手順です。

- 毎日の確認は、原則として上から順番に行う
- 異常がない項目は深追いしない
- 実API呼び出し、動画生成、クレジット消費、本番DB書き込みは行わない
- 異常を見つけた場合は、先に記録を残してから対応する
- 決済、返金、認証、アカウント停止、削除は、対象を再確認してから実行する

## 毎日

### 1. 本番サイト

- [ ] `https://www.pinastudio.jp/`が開く
- [ ] ログイン画面と生成画面が表示される
- [ ] 画面崩れや重大なエラー表示がない

問題がある場合は、発生日時、対象URL、画面表示、直前の変更を記録する。

### 2. 管理画面

- [ ] `admin.html`へ管理者としてログインできる
- [ ] Supabase DBの接続状態が正常
- [ ] 処理待ち・処理中のタスクが長時間止まっていない
- [ ] 失敗タスクが急増していない
- [ ] 最近の生成タスクに不自然な重複がない

`admin.html`の数字だけで原因を断定しない。必要な場合は、対象タスクIDを控えてからVercelログやSupabaseを確認する。

### 3. 問い合わせと通報

- [ ] FormspreeのInboxを確認する
- [ ] FormspreeのSpamも確認する
- [ ] 未対応の問い合わせがない
- [ ] `category: content_report`または`priority: urgent`の通報がない

通報を受けた場合は、`docs/operations/CONTENT-REPORT-PROCEDURE.md`に従う。危険な画像やリンクを不用意に開かない。

### 4. Stripe

- [ ] 失敗した支払いが急増していない
- [ ] 未処理または失敗したWebhookがない
- [ ] 不審な返金や重複決済がない
- [ ] サブスクリプションの異常な増減がない
- [ ] 当日の成功決済ごとに、対応するSupabase上のクレジット付与記録と残高反映がある

成功決済とクレジット付与を照合する場合は、Stripeの顧客ID・決済IDと、SupabaseのユーザーID・クレジット取引記録を突き合わせる。確認だけでは返金、クレジット再付与、契約変更を実行しない。不一致があれば対象IDと確認結果を記録して、追加操作を止める。

### 5. VercelとRailway

- [ ] VercelのProductionが正常
- [ ] 最新デプロイが失敗していない
- [ ] Functionエラーが急増していない
- [ ] Railwayのwatermark-serverが停止していない
- [ ] Railwayのエラーが急増していない

障害が疑われる場合は、サービス名、発生日時、対象処理、エラー内容を記録する。

### 6. 外部APIの利用額

- [ ] OpenRouterの残高不足や急増がない
- [ ] OpenAIの利用額が急増していない
- [ ] Anthropic等、現在使用中の外部APIで異常な利用がない
- [ ] 各サービスの障害情報が出ていない

利用額が急増している場合は、新規生成を繰り返して原因確認をしない。対象時間帯と呼び出し元を先に調べる。

### 7. 実施記録

異常がなければ、日付と「異常なし」だけを記録する。

異常がある場合は、最低限次を記録する。

- 確認日時
- 確認者
- 対象サービス
- 発生内容
- 対象ユーザーID・タスクID・決済ID等
- 実施した対応
- 未完了の対応
- 次回確認日時

秘密情報、APIキー、パスワード、カード情報、画像本体は記録しない。

## 毎週

- [ ] 生成成功・失敗の傾向を確認する
- [ ] Stripe Webhook失敗の有無を確認する
- [ ] サブスクリプション加入・解約の増減を確認する
- [ ] モデレーション拒否の急増や偏りを確認する
- [ ] Vercel、Railway、OpenRouter等の障害履歴を確認する
- [ ] バックアップ状況を確認する
- [ ] 未完了の問い合わせ・通報・返金対応を見直す

## 異常を見つけた場合

1. 追加操作を止める
2. 日時、対象、エラー内容を記録する
3. 影響範囲を確認する
4. 決済、認証、DB、生成機能に関わる場合は、勝手に修正・返金・削除しない
5. 緊急停止・障害対応手順が完成するまでは、本番設定やDBを変更せず、Vercel・Railway・Stripeの状態と直前の変更を確認して、状況を記録したまま作業を停止する
6. 緊急停止・障害対応手順の完成後は、その手順書を優先する

## この文書の範囲

この文書は、日々の確認順序を定めるものです。自動監視、管理画面の機能追加、返金実行、アカウント停止、データ削除、障害復旧そのものは含みません。
