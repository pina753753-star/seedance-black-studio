# Pina Studio 緊急停止・障害対応手順

Pina Studioで障害、不正利用、決済異常、情報漏えいの疑いなどが発生した場合に、被害を広げず安全に確認・停止・復旧するための運営手順です。

## 基本原則

- 最初に追加操作を止め、発生日時と確認できた事実を記録する
- 推測だけで原因を断定しない
- 障害調査のために新規動画生成を繰り返さない
- 実API呼び出し、動画生成、クレジット消費、本番DB書き込みは、事前承認なしで行わない
- 決済、返金、契約変更、アカウント停止、データ削除は、対象を再確認してから行う
- 複数の変更を同時に行わず、停止、修正、復旧確認を1段階ずつ行う
- APIキー、シークレット、パスワード、カード情報、画像本体を対応記録へ残さない

## 1. 緊急度の分類

### 緊急

直ちに確認を開始し、必要に応じて対象機能を停止する。

- 児童の性的搾取・CSAM疑い
- 実在人物へのなりすましや非同意の性的画像
- APIキー、認証情報、個人情報の漏えい疑い
- 不正な決済、返金、クレジット付与が継続している
- 多数のユーザーへ誤課金、二重課金、クレジット消失が発生している
- 管理者アカウントや本番環境への不正アクセス疑い
- 本番DBの破損、消失、意図しない大量更新
- サービス全体が利用不能

### 高

原則として当日中に確認を開始する。

- 動画生成が広範囲で失敗している
- クレジット控除後に動画が生成されない事例が複数ある
- Stripe決済成功後にクレジットが付与されない
- Webhook失敗が継続している
- Railway、OpenRouter、OpenAI、Supabase等の障害で主要機能が使えない
- モデレーションが動作していない疑い
- 問い合わせや通報を受信できない

### 中・低

日次運営チェックへ記録し、通常の修正手順で対応する。

- 一部画面の表示崩れ
- 単発の生成失敗
- 一時的な外部サービス障害
- 利用者への影響が限定された軽微な不具合

## 2. 最初の5分で行うこと

1. 追加の操作や変更を止める
2. 発生または発見日時、対象画面・サービス、エラー内容、対象ID、直前の変更を記録する
3. 影響が1人だけか複数か、生成・決済・認証・DBのどこか、現在も被害が増えているかを確認する
4. 対象サービスの公式障害情報を確認する
5. 原因が分からない状態で返金、削除、再付与、DB修正を行わない

## 3. 状況確認の順番

### 本番サイト

- `https://www.pinastudio.jp/`が表示されるか
- ログイン画面・生成画面・管理画面に重大なエラーがないか

### Vercel

- Productionの最新Deploymentが`READY`か
- 直前のDeploymentとcommit
- Functionsログの反復エラー
- 独自ドメインとVercel標準URL
- Previewは正常でProductionだけ異常か

### Supabase

- Auth、Database、Storageの公式障害情報と各ログ
- 対象ユーザー、生成タスク、クレジット取引の状態
- 意図しない大量更新や削除の有無

確認だけでSQL更新、ユーザー削除、クレジット変更を行わない。

### Stripe

- Payments、Subscriptions、Customer、Webhook履歴
- 同じイベントの失敗・重複処理
- Stripe上の成功決済とSupabase上の契約・クレジット反映

確認だけで返金、契約取消、再請求を行わない。

### Railway

- watermark-serverの稼働・デプロイ状態・エラーログ
- `/watermark`または動画編集処理の失敗傾向
- 直前の設定変更やデプロイ

確認のために実動画を送信しない。

### OpenRouter・OpenAI等

- 公式障害情報、利用額、残高、認証エラー、レート制限
- 対象時間帯の呼び出し元

原因確認のために新規生成を繰り返さない。

## 4. 機能停止の判断

### 生成機能

次の場合は停止を検討する。

- モデレーションが動作していない
- クレジット控除や返金が正常に動作していない
- OpenRouter等への異常な連続送信が発生している
- 不適切コンテンツが安全確認を通過している疑い
- 生成失敗が広範囲で継続している

既存の参照画像生成停止は`api/seedance-start-priced.js`で、クレジット控除やOpenRouter呼び出しより前にHTTP 503を返す方式を採用している。

ただし、Production環境変数`TEST_BYPASS_USER_ID`が設定されている場合、指定されたテストユーザーだけはこのHTTP 503停止を回避できる。緊急停止時は設定の有無を確認し、無効化確認が終わるまでは参照画像生成が完全停止したと判断しない。

`TEST_BYPASS_USER_ID`の無効化が必要な場合も、Production環境変数を無断変更しない。現在値そのものを記録・共有せず、影響範囲と戻し方を確認し、ユーザーの明示承認後に変更する。

生成機能全体を止める具体的な変更は、現状コードを確認して完成形を作成し、Preview確認後に反映する。緊急時でも環境変数やAPIコードを推測変更しない。

### 決済

決済成功後の反映失敗、二重課金、誤価格、誤付与、キー漏えい疑いが継続する場合は新規決済停止を検討する。Stripeの商品、価格、Webhook、契約を直接削除しない。

### 認証

年齢確認やメール確認の回避、管理画面の権限不備、認証情報漏えい疑いがある場合は新規登録やログイン停止を検討する。既存ユーザーを一括削除・一括ログアウトしない。

### DB

意図しない大量更新・削除、マイグレーション失敗、不整合の増加、対象行を特定できない場合は本番DBへの書き込みを止める。追加SQLを重ねず、実行済みSQL、対象行、件数、時刻を記録する。

## 5. ロールバック

### Vercel

1. 現在のProduction Deploymentとcommitを記録する
2. 直前に正常だったDeploymentを特定する
3. DB変更や環境変数変更との依存を確認する
4. コードだけ戻して不整合が起きないことを確認する
5. ユーザー承認後にロールバックする
6. 本番サイト、ログイン、管理画面、生成開始前までを確認する

実動画生成、決済、クレジット消費を伴う確認は別途承認を得る。

### GitHub

- 履歴を書き換えず、mainへのforce pushを行わない
- 原則としてrevert commitまたは修正PRを使う
- 対象commit、理由、影響範囲を明記する
- 無関係な変更を同時に戻さない

### Supabase

- DB変更を推測で逆戻ししない
- 適用済みマイグレーションと実際のDB状態を確認する
- データを失う可能性があるSQLを実行しない
- バックアップと復元可能性を確認する
- 完成形SQLと対象件数を事前確認し、ユーザー承認後に実行する

## 6. メンテナンス表示

案内には、利用できない機能、調査中であること、課金やクレジットへの影響を確認中であること、復旧後に案内することだけを記載する。原因未確定の段階で、データ消失、漏えい、返金確定等を断定しない。

## 7. 復旧確認

1. Vercel、Supabase、Stripe、Railway等が正常
2. 本番サイト、ログイン画面、管理画面が正常
3. 異常ログや件数が増えていない
4. StripeとSupabaseの不整合が解消または隔離済み
5. 停止機能を段階的に再開
6. 実API、動画生成、決済を伴う最終確認は事前承認後に実施
7. 利用者へ復旧案内
8. `STATUS.md`へ対応記録を残す

正常確認前に複数機能を同時に再開しない。

## 8. 利用者への告知基準

- サービス全体または主要機能が長時間利用不能
- 課金、契約、クレジットへ影響
- ユーザーデータへ影響した可能性
- 利用者側で再操作や確認が必要
- 同じ障害が再発する可能性

個別ユーザーだけに影響する場合は、本人確認後に個別連絡する。

## 9. 事後記録

発生・発見・復旧日時、緊急度、影響機能、対象件数、確認できた原因、停止機能、実施変更、commit・PR・Deployment、DB操作、決済・返金・クレジット対応、告知、再発防止策、未完了事項を記録する。確認できないことは「確認できません」と記録する。

## 10. 絶対に単独判断で行わない操作

- 本番DBの更新・削除
- ユーザーアカウントの停止・削除
- Stripeの返金、契約取消、商品・価格削除
- クレジットの手動付与・減算
- APIキーやシークレット、Production環境変数の変更
- mainへのcommit、push、PR作成、merge
- Vercel Productionのロールバック
- Railway Productionの設定変更・再デプロイ
- 実API呼び出し、動画生成、決済を伴うテスト

対象、影響範囲、戻し方を確認し、ユーザーの明示承認を得てから行う。
